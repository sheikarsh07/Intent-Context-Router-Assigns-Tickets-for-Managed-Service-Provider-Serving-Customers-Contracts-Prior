2. BASELINE TEXT ROUTER ARCHITECTURE (36% - 45% WORKLOAD)
--------------------------------------------------------------------------------
To evaluate performance gains objectively, a text-only baseline model (`src/baseline.py`) was implemented as a control benchmark.

Specification & Implementation (`BaselineRouter`):
- Feature Extraction: `TfidfVectorizer` (unigrams and bigrams, English stop-word filtering).
- Classifier Model: `LogisticRegression` (multinomial classification, max_iter=1000, random_state=42).
- Inputs: Raw `ticket_text` string.
- Outputs: Predicted `correct_resolver` and classification confidence score.
- Design Boundary: The baseline strictly evaluates ticket description text without access to organization, contract, asset, user role, or historical assignment data.

3. TECHNICAL INTENT CLASSIFICATION ENGINE (45% - 53% WORKLOAD)
--------------------------------------------------------------------------------
The intent detection engine (`src/intent.py`) translates unstructured support text into technical intent categories.

Intent Classes & Primary Target Mappings:
- `VPN Issue` -> Primary Target: Network Team
- `Database Outage` -> Primary Target: Database Team
- `Hardware Fault` -> Primary Target: Hardware Team
- `Security Incident` -> Primary Target: Security Team
- `Application Crash` -> Primary Target: Application Team
- `Cloud Outage` -> Primary Target: Cloud Team

Security Interceptor Mechanism:
To guarantee critical security threats are never misclassified by pure text models, a rule-based interceptor inspects raw text for critical security indicators (`ransomware`, `phishing`, `exfiltration`, `unauthorized`, `exploit`). If detected, the intent is forced to `Security Incident` with a floor confidence of 0.95 and primary target `Security Team`.

4. MATHEMATICAL FORMULATION OF HYBRID OBJECTIVE FUNCTION (53% - 60% WORKLOAD)
--------------------------------------------------------------------------------
The routing decision is governed by a hybrid objective function that mathematically combines hard constraint binary step functions with soft constraint weighted scoring terms.

Hybrid Objective Function Equation:
  Final_Score(r, T) = H_c(r, T) * [ W_intent * S_intent(r) + W_asset * S_asset(r) + W_policy * S_policy(r) + W_contract * S_contract(r) + W_prio * S_prio(r) - P_bounce(r) ]

Where:
- r: Candidate resolver group in RESOLVER_GROUPS.
- T: Support ticket payload (text, org, asset, role, priority, contract, history).
- H_c(r, T) in {0, 1}: Binary Hard Constraint Step Function. Returns 0 if candidate r violates any hard security, contract policy, partner access, or priority restriction. If H_c(r, T) = 0, the final score is strictly 0.0 (Hard Rejection).
- S_intent(r) in {0, 1}: 1 if candidate r matches primary resolver for predicted intent; 0 otherwise (W_intent = +35.0).
- S_asset(r) in {0, 1}: 1 if candidate r matches primary resolver for asset type; 0 otherwise (W_asset = +25.0).
- S_policy(r) in {0, 1}: 1 if candidate r is approved for customer organization (W_policy = +10.0).
- S_contract(r) in {0, 1}: 1 if candidate r matches contract SLA tier (W_contract = +10.0).
- P_bounce(r): Previous Bounce Penalty. Subtracts 30.0 if candidate r matches previous_resolver or exists in assignment_history.

Handling Conflicting Metadata:
When ticket text and asset metadata conflict (e.g., text describes a Cloud VM script crash while asset is listed as Laptop), the weighted scoring framework balances Intent Match (+35.0) against Asset Match (+25.0). In this scenario, Cloud Team scores 35.0 (intent match), whereas Hardware Team scores 25.0 (asset match), allowing intent to govern while logging medium confidence for review.

--------------------------------------------------------------------------------
5. HARD & SOFT CONSTRAINT ENGINE IMPLEMENTATION (60% - 65% WORKLOAD)
--------------------------------------------------------------------------------
The constraint module (`src/constraints.py`) enforces business rules and ranks candidates.

Hard Constraints (Layer 1 - Strict Filters):
1. Security Authorization Rule: Security Incident strictly requires Security Team.
2. Organization Policy Rule: Customer contract limits allowed resolver groups.
3. External Partner Role Rule: External Partner roles restricted to approved partner teams.
4. Priority Limit Rule: Critical priority tickets restricted to teams with Critical handling capability.

Soft Constraints (Layer 2 - Weighted Scoring):
Calculates scores using `config.SOFT_WEIGHTS`: Intent Match (+35.0), Asset Match (+25.0), Org Match (+10.0), Contract Tier (+10.0), Policy Fallback Boost (+25.0 for Application Team when primary team is restricted), and Bounce Penalty (-30.0 for previously failed teams).

--------------------------------------------------------------------------------
6. CONTEXT-AWARE ROUTING PIPELINE (65% - 70% WORKLOAD)
--------------------------------------------------------------------------------
The main routing module (`src/router.py`) integrates all sub-components into an end-to-end pipeline (`ContextAwareRouter`).

Pipeline Steps:
1. Intent Detection: Predicts intent and confidence via `IntentClassifier`.
2. Candidate Evaluation Loop: Evaluates Hard Step Function H_c(r, T) and Soft Score for all 6 resolver groups.
3. Selection & Confidence: Ranks eligible candidates by Final_Score. Selects top resolver group and estimates confidence score:
   Confidence = Clip( (Top_Score / 85.0) * 0.60 + (Intent_Confidence * 0.40), 0.35, 0.99 )
4. Explainable Rationale: Generates human-readable bullet points detailing score components, hard constraint validations, and rejected candidate reasons.
